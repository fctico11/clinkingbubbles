============================================================
WHY THIS WORK STARTED
============================================================
Goal: improve organic/SEO visibility. Competitor research identified
"Stiiir" (stiirbar.com), a mobile bar company in NJ ranking #1 for
the kind of searches Clinking Bubbles wants to win. Stiiir's site has
~52 pages vs. our 7 at the time; the gap is almost entirely
programmatic local-SEO landing pages (county pages, town pages,
event-type pages) plus a real information architecture (not a flat
page list). We reverse-engineered their structure via live site
inspection (not scraped/copied content — original copy was written
for every page, and Stiiir's exact chip/pill visual style was
deliberately NOT copied per user instruction — see "DESIGN DECISIONS"
below) and are replicating the STRATEGY, not the content.

Stiiir also uses a third-party tool called "Flashquotes"
(flashquotes.com) for instant booking/quotes — noted but NOT adopted;
out of scope for now.

============================================================
CROSS-LINKING / INTERNAL LINK MESH
============================================================
Every location page and every event-type page is now mutually linked:
  - Location pages -> event-type pages via the "Planning a different
    kind of event?" line inside the new PageCTA component.
  - Event-type pages -> location pages via the "Also serving:" line,
    also inside PageCTA.
  - Each of the 6 town-level pages (5 Union County towns + Saddle
    River) also has a "NearbyTownsStrip" — real bordering-municipality
    data pulled from Wikipedia geography sections (verified per town,
    not guessed), rendered as flowing prose. Where a bordering town
    has its own page, it's a real link; otherwise it's plain text
    (adds long-tail geo keyword coverage without a dead link or a
    fabricated page).
No page in the location/event tree is an orphan; click-depth to
anything from anywhere is small.

============================================================
KEY DESIGN DECISIONS (so future-me doesn't redo this thinking)
============================================================
1. Hub-and-spoke, not flat nav. Nav only shows /services, /packages,
   /service-areas — NOT individual town or event-type pages. This
   matches Stiiir's actual nav (they only nav-link counties/flagship
   cities, not every town) and avoids nav clutter as inventory grows.

2. Union County: NOT all 21 towns get dedicated pages. Only 5 with
   real event/wedding-venue density (Summit, Westfield, Berkeley
   Heights, Cranford, Scotch Plains) got pages; the other 16 are
   covered by name in the county hub's prose only. Reasoning: near-zero
   search volume for hyper-small towns, and avoiding Google's "scaled
   content abuse" pattern (many near-identical thin pages).

3. Pill/chip badge UI was tried, then explicitly rejected by the user
   as "exactly the same as Stiiir" (too literal a copy of their visual
   language) and because two pill blocks stacked at the page bottom
   read as a link dump. Replaced with:
     - NearbyTownsStrip: flowing prose sentence, not badges.
     - Event-type / service-area cross-links: folded into PageCTA as
       small underlined text links, not a separate section.
   Placement was also fixed: NearbyTownsStrip now sits mid-page (right
   after the "Serving X & Union County" section), separated from the
   bottom CTA by the entire FAQ section — not stacked together.

4. PageCTA component (src/components/PageCTA.js) — new shared CTA used
   on all 11 location/event pages. Deliberately matches the visual
   language of the user's own (still-uncommitted) GetStartedSection.js
   (gold gradient "Request Your Free Quote" button, gold-accent divider,
   cream background) but is CSS/AOS-driven instead of framer-motion,
   specifically to avoid pulling framer-motion into 11 separate lazy
   page chunks. GetStartedSection.js itself is Home-page-only and
   still has the known perf caveat noted in the earlier memory file
   (statically imports framer-motion; not yet resolved, not this
   session's problem to fix unless asked).

5. /services vs /packages split: the OLD /services page (which had
   pricing tiers) already had SEO history at that URL. New content
   (event-type hub) was put AT /services (same URL, new meaning) and
   the pricing content moved to a brand-new URL /packages (starts with
   zero authority). This was a deliberate tradeoff, flagged to the user:
   watch Search Console after launch to see how /services reindexes
   under its new topic and how /packages ramps up separately.

6. Rollout batching / scaled-content-abuse risk: discussed at length.
   Conclusion reached: the current batch (~19 total pages, up from 7)
   is fine to push as ONE deploy because every page has genuinely
   differentiated content and sits in a real hierarchy (not flat
   duplication). BUT: recommended pausing further NEW PAGE CREATION
   for a few weeks after this deploy, to (a) let Google digest this
   batch, and (b) gather Search Console data on how /services vs
   /packages settle before adding more volume. This pause has NOT
   formally started yet because nothing has been pushed live yet.
